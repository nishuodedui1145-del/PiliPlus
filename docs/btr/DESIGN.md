# BTR 多 Range 并发加速 —— 设计与实现

> 本文记录这个移植的**设计决定**与**为什么**。每一条都是真机实测换来的，不是推演出来的。
> 面向想改这套代码的人：先读本文，再看 `lib/services/btr_proxy/`。

## 1. 背景

海外看 B 站，冷门视频 / 4K 经常「一直转圈、加载卡死」。原因不是本地带宽，而是
**单条 TCP 连接被 CDN 限速**（实测每条连接 0.05~0.5 MB/s 很常见）。

[Bilibili-thread-ripper](https://github.com/Neko-77/Bilibili-thread-ripper)（BTR）在浏览器里解决了这个问题
（改 MSE/DASH 层做多 Range 并发）。但安卓客户端是 Kotlin/Dart + ExoPlayer/mpv，**JS 塞不进去**。

## 2. 架构选择：本地 HTTP 代理

```
mpv ──▶ http://127.0.0.1:<port>/media?u=<base64 上游地址>&th=…&k=video|audio&g=…
                    │
                    ├─ proxy_server.dart      本地 HTTP 服务：Range 解析 / 206 / HEAD / 顶头兜底 / 透传
                    ├─ cdn_pool.dart          CDN 候选池：分组、host 替换、粘性、拉黑、竞速提示
                    ├─ multi_range_downloader.dart  分块调度：并发、hedge、慢块补救、模式切换、降级
                    ├─ cdn_racer.dart         进视频后后台竞速候选节点（TTL 缓存）
                    └─ range_core.dart        常量与阈值契约（码率解析、期望耗时、迟滞）
```

**为什么要代理而不是改播放器**：播放器（mpv）不可控；代理是唯一能同时满足
「复用播放器全部能力」+「字节级可控」的位置。代价是所有数据多走一次本地回环（无加密开销，实测可忽略）。

## 3. 关键设计决定

### 3.1 码率单位：`bw` 是 bit/s
上游地址的 `bw` 参数（如 `bw=19240000`）单位是 **bit/s**，必须 **÷8** 才是字节/秒。
曾经把它当 byte/s → 目标速率、慢块阈值、并发反推、单/多连接门限**全链路虚高 8 倍** →
并发开爆 → 触发节点限流 → "线程越多越慢"。
判据：`yt-dlp -F` 给出的码率与 `bw/8` 严格对齐（`bw=155643 ↔ 156kbps`）。

### 3.2 响应头必须尽早发出（Dart 的特性）
播放器读响应头有超时（ffmpeg 约 4~5 秒）。代理在拿到首块数据前不发头 → 直接超时重试死循环。
**实测结论：Dart `HttpServer` 只 `flush()` 不会发出任何字节，必须写入 ≥1 字节 body 才会真正发头。**
→ 兜底策略：`_fetchPrimerByte()` 先取 **1 字节** 顶出响应头，随后从 `start + 1` 继续流式写（无缺口、无重复）。

### 3.3 顶头兜底必须回精确 206
若顶头时回 `200` 且没有 `Content-Length`，播放器拿不到总长度 → `Seek failed (to N, size -38)`
→ 反复小偏移重试 → 越试越卡。→ 必须回 **精确 `206` + `Content-Range` + `Content-Length`**，
且后续写入要有 `endOffset` **硬上限**（绝不多写一字节）。

### 3.4 并发数是「反推」出来的，不是开满
`目标 = 码率 × 1.2`（无码率时兜底 1 MB/s）；`目标并发 = ceil(目标 / 每连接实测速度)`；
一次自适应决策最多爬升 8 条（避免抖动）。官方文档也写明「线程不是越多越快，甚至触发节点限制」。

### 3.5 在途连接数必须双向调整
曾出现 `setConcurrency()` **只增不减** → 配置上限降到 8 后内部预算仍是 34 → hedge 把在途撑到 27 条
→ 自我限流（多连接聚合 0.17 MB/s，而单连接 2.14 MB/s）。现在预算双向更新，超预算时 **hedge 排队而不是新建连接**。

### 3.6 单/多连接切换：判据互斥 + 迟滞 + 驻留
真机出现过 **1~2 秒互切一次**（每次掐断流）。根因是两条规则同时成立：
「多连接比单连接快不了多少」≠「单连接够用」。
现在：
- 切入单连接：必须 **单连接 ≥ 多连接 × 0.95**（多连接更快就绝不切）；
- 切回多连接（解粘）：**对比式** —— 切入时记下 `multiBpsAtSwitch`，需连续 3 个区间不达标**且**当初多连接明显更好；缺数据不解粘；
- **最小驻留 20 秒 + 每视频每分钟 ≤2 次**。

### 3.7 分块失败绝不跳块
fMP4 跳块会花屏。任何分块彻底失败 → **降级为单连接顺序透传**把整个区间写完（宁可慢，不能坏）。

### 3.8 慢块阈值是动态的
`期望耗时 = 分块字节 / (目标 ÷ 目标并发)`，超过 **1.6×** 判慢，夹在 400~3000ms，无信息时回退 1200ms。
且**只在自适应决策点更新**（否则阈值本身抖动会引发补救风暴）。

### 3.9 CDN 竞速：进视频后台跑，不阻塞起播
- 不能"app 启动就跑"：没有真实播放地址测不出**吞吐**（只能测握手延迟）；且 CDN 速度**分钟级波动**
  （实测同线路一分钟内 0.19 → 1.36 → 10.43 MB/s）。
- 因此：**进视频时后台竞速**（6 候选 × 64KB，预算 800ms，并行窗口 2），结果 **TTL 300 秒** 复用；
  请求路径**只读缓存，绝不 await 竞速**；全失败则**不改动任何现役状态**。
- **迟滞 1.2×**：新结果必须快 20% 以上才替换现役，否则每次启动都选到不同节点，体验更差。
- 锚点优先级：**视频自身给的 host > 竞速最优 > 其它候选**（竞速只补位纠偏）。

### 3.10 生命周期：代理不能随便停
从"历史记录"进入视频时，旧控制器的 `onClose()` 会先跑。若那里直接 `stop()`（`close(force: true)`），
端口立即失效，而**新播放器手里的 URL 还指向旧端口** → `Failed to open` → 黑屏，用户得手动重载。
→ 改为 **`scheduleStop(delay: 5s)`**：期间只要出现新的 `ensureStarted()` 或**任何客户端请求**就取消停止；
`stop()` 本身也加兜底：有在途请求、或最近 3 秒内有活跃请求 → 跳过停止。

### 3.11 慢块补救（hedge）
块在阈值内没到就补第二路抢结果，**但仅当聚合速度 < 目标时才允许** ——
聚合已达标还去抢，只会白白多占空口（真机上看到它压制了十几次无谓 hedge）。

## 4. 参数一览（`range_core.dart` 为准）

| 参数 | 值 | 说明 |
|---|---|---|
| `defaultMaxPieceBytes` | 512KB | 分块大小 |
| `defaultStartupProbeChunkBytes` | 64KB | 启动探测样本 |
| `startupProbeTotalTimeout` | 400ms | 启动探测总预算 |
| `firstResponseDeadline` | 1800ms | 超时改「1 字节顶头」 |
| `slowPieceFactor` | 1.6 | 慢块判定倍率（夹 400~3000ms） |
| `switchBackMargin` | 15% | 模式切换迟滞 |
| `maxRampConcurrency` | 8 | 单次决策最多爬升 |
| `kUnknownBitrateFallbackBps` | 3.0 MB/s | 无码率兜底目标 |
| 竞速 | TTL 300s / 迟滞 1.2× / 6 候选 / 64KB / 预算 800ms | `cdn_racer.dart` |
| strike | 2 次 | 半死节点拉黑门槛 |
| 退避 | `min(60, 3×2^failures)` 秒 | 失败节点退避 |

## 5. 测试策略

1. **单元契约**（`btr_bitrate_unit_test.dart`）：码率单位、阈值上下限、期望耗时 —— 防止"数值悄悄漂移"。
2. **竞速**（`btr_cdn_racer_test.dart`）：本地起 3 个**速度可控的假 CDN** → 断言选最快 / 坏节点不影响 /
   全失败不改状态 / 迟滞保持与替换 / TTL 过期 / 样本上限。
3. **端到端**（`btr_proxy_e2e_test.dart`）：对**真实 CDN 直链**验证代理返回字节与直连**逐字节一致**，
   含封闭区间、开放式区间、越界（EOF）、坏签名 403 等用例。
4. **镜像测试台**（`tool/make_btr_mirror.py`）：把代理模块镜像成不依赖 App 的独立目录再跑测试 ——
   **所以 `lib/services/btr_proxy/` 严禁 import App 层代码或 `Pref`**，否则测试台失效。
5. 真机：每轮改动都装机，用 `adb logcat` 抓 `[BTR]` 埋点核对（埋点只打 host，禁止打带签名的完整 URL）。

## 6. 未来方向（未做）

- **把竞速结果写回 App 的 CDN 设置**（`Pref.defaultCDNService`）：收益更大（关掉 BTR 也生效），
  但会改到别的功能的设置项，需谨慎。
- 跨节点 `total` 长度一致性校验；hedge 提升到 3 路；分块缓存上限。
- 高码率流是否用更小分块（512KB → 128~256KB）以降低起播延迟。
